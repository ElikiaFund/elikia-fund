# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A monorepo for the Elikia Fund fintech MVP: an offline-first cash flow tracker, a savings vault, and group savings circles ("tontines"), built as three independent apps talking to one Laravel API. The sprint scope, day-by-day plan, and cut list live in [`fintech-mvp-one-week-plan.md`](fintech-mvp-one-week-plan.md) — read it before making product/scope decisions; it is the source of truth for what's in vs. out of scope for the current sprint, not this file.

```
api/           Laravel 13 + Sanctum + MySQL
mobile/        Expo (React Native + TypeScript) — end-user app
back-office/   Vite + React + shadcn/ui — admin app
website/       Next.js marketing site (French, 4 pages) — reuses the mobile/back-office brand system, see website/README.md
```

Each app has its own `README.md` with setup steps — this file covers cross-cutting architecture and commands.

## Commands

### api/ (Laravel)
```
composer install
cp .env.example .env && php artisan key:generate
php artisan migrate:fresh --seed  # seeds 2 staff logins (Super Admin + read-only Support) + ~30 realistic users/transactions/companies/tontines
php artisan storage:link          # serves uploaded avatars
php artisan serve                 # http://localhost:8000/api

php artisan route:list --path=api # inspect registered routes
./vendor/bin/pint                 # format (run before committing PHP changes)
php artisan test                  # or: ./vendor/bin/phpunit
php artisan test --filter=TestName
```

### mobile/ (Expo)
```
npm install
cp .env.example .env
npx expo start

npx tsc --noEmit                  # type-check
npx expo lint
npx expo-doctor                   # validates SDK/plugin config
```
Google and Facebook sign-in require a custom dev client (`npx expo run:ios` / `run:android`, or an EAS dev build) — they don't work in plain Expo Go, because `@react-native-google-signin/google-signin` and `react-native-fbsdk-next` ship native code. Apple sign-in works in Expo Go.

### back-office/ (Vite + React)
```
npm install
cp .env.example .env
npm run dev

npx tsc -b                        # type-check
npm run build                     # tsc -b && vite build
npm run lint                      # oxlint
```

## Architecture

### Auth is split by app, not shared
- **Mobile (end users): OAuth (Google/Apple/Facebook) + email/password.** `POST /auth/google|apple|facebook` verify the provider token server-side (`api/app/Services/SocialAuthService.php`) and find-or-create the `User` by provider id, falling back to email match. The Apple flow **decodes the identity token without verifying its signature** — see the `TODO` in `SocialAuthService::decodeAppleToken()` before shipping (needs JWKS verification via `firebase/php-jwt`). `POST /auth/register`/`POST /auth/login` (`Api\AuthController`) are the plain email/password path — register rejects a duplicate email outright (`unique:users,email`) rather than silently attaching a password to an existing OAuth account by email match, which would let anyone who knows a victim's email hijack their account; linking a password onto an OAuth-created account is only possible authenticated, via `PUT /me`.
- **Back office (staff): email + password.** `POST /admin/login`, rejected unless the account has a `role_id`. Staff are seeded (`database/seeders/DatabaseSeeder.php`) or created via the Personnel page (`/personnel`), never self-registered.
- Both flows land on the same `users` table and issue Sanctum personal access tokens; `POST /logout` and `GET /me` work for either caller. `PUT /me` / `POST /me/avatar` (profile edit, avatar upload) work for either too.
- Mobile and back-office each have their own `src/services/apiService.ts` — a single axios instance per app (base URL + bearer token injection + French error normalization). New API calls go through it; don't spin up a second axios instance in either app.

### Vault PIN — a property of the person, not the vault
The vault requires a 4-digit PIN, set on first activation, not just a one-time gate — but the PIN itself (and its lockout state) lives on `users.pin_hash`/`pin_set_at`/`failed_pin_attempts`/`locked_until`/`lockout_count`/`lockout_count_reset_at`, **not** on `vaults`. Deliberate: one shared PIN across every company vault a person can reach, a foundation for a later feature where several users on one company each use their own PIN against that company's single shared vault (not built yet).
- `POST /vault/activate` — first call ever (`! $user->has_pin_set`) sets the shared PIN (`Hash::make`); every subsequent company's activation (`$user->has_pin_set` already true) instead re-verifies the existing PIN before creating that company's vault, via `VaultSecurityService::checkPin(User $user, Vault $vault, string $pin)`.
- `POST /vault/pin/verify` re-checks the PIN and is rate-limited (5/min) — the mobile Coffre tab calls this **every time it regains focus** (`src/context/vault-context.tsx` tracks unlock state per company id, resetting whenever the active company changes), not just once per session.
- `pin_hash` is deliberately excluded from `User::$fillable` (set via direct attribute assignment only) and from JSON output (`#[Hidden(['pin_hash'])]`) — never make it mass-assignable or serializable. `User::has_pin_set` is a computed `$appends` attribute (mirrors `is_admin`) so mobile can branch its vault-activate UI (choose a new PIN vs. confirm the existing one) without exposing the hash itself.
- All `/vault/*` routes (including the PIN-only ones) sit inside the `resolve-active-company` middleware group — a `VaultSecurityEvent` always logs against a specific `vault_id` (required, non-nullable FK), so even a pure PIN check needs to know which company's vault it's acting on.

### Cash flow: SQLite only when offline (mobile)
Cash flow is the only feature with a local fallback at all (vault and groups are online-only, per the sprint plan) — but it is **not** local-first: `mobile/src/lib/transactions.ts#loadTransactions()` reads straight from `GET /transactions` whenever the device is connected (accurate across devices, not just whatever synced to this one), mirrors the result into the local `expo-sqlite` cache (`mobile/src/db/database.ts`, `transactions`/`sync_queue` tables) via `cacheSyncedTransaction(s)`, and merges in any still-unsynced local rows so an offline-created transaction doesn't vanish from the list the instant the app reconnects but before the sync flush lands. `add-transaction.tsx` mirrors this: online, it `POST`s to `/transactions` directly and caches the confirmed row; only when offline (or the online request itself fails) does it fall back to `insertTransaction()` + `sync_queue`, exactly as before. `flushSyncQueue()` still flushes `sync_queue` to `POST /sync` in batches on reconnect, last-write-wins by timestamp, client-generated UUIDs so offline records never collide — that part is unchanged, it just now only matters for the offline-write path.
- Every local table (`transactions`, `sync_queue`, `cash_sessions`, `cash_session_sync_queue`, `cash_session_active`) carries both `user_id` and `company_id` — scoping queries key off `company_id` alone (sufficient and more precise than the pair), while `user_id` is kept alongside for payload shape and the composite `cash_session_active` key. `backfillLegacyIds(userId, companyId)` is a one-time, idempotent backfill for rows written before per-user, then per-company, scoping existed — it runs from `company-context.tsx` once an active company is resolved (not from `auth-context.tsx`, where no company is known yet).

### Data model
`users` (nullable `password`, nullable `google_id`/`apple_id`/`facebook_id`, nullable `onboarding_completed_at`, nullable `role_id`, + PIN/lockout columns — see "Vault PIN"), `roles` (+ `permissions`, + `permission_role` pivot), `companies`, `transactions`, `products` (+ `product_categories`, `stock_movements`), `vaults` (+ `vault_movements`, `company_id` FK unique), `groups` (+ `group_members`, `contributions` — both carry `company_id`). Full relationships are wired on the Eloquent models in `api/app/Models/`. `sync_queue` is mobile-local only, not an API table.

`is_admin` is a **computed** attribute now (`User::isAdmin()`, `role_id !== null`), not a column — kept as a real JSON field via `$appends` so every existing `is_admin` consumer (mobile, back-office Users page) kept working unchanged when roles replaced the old boolean. Don't re-add `is_admin` as a migrated column; the source of truth is `role_id`.

### RBAC (roles & permissions) and Personnel
Full custom RBAC: `permissions` is a **fixed, code-defined catalog** (`PermissionSeeder::catalog()`, 12 keys across 6 groups) — not user-creatable, only assignable to roles. Admins create/edit `roles` and toggle which permissions each grants (`Admin\RoleController`, back-office `/personnel` → "Rôles & Permissions" tab). "Personnel" (internal Elikia staff, `/personnel` → "Personnels" tab) is **the same `users` table** filtered to `role_id IS NOT NULL` (`Admin\PersonnelController`) — consumers (mobile app users) always have `role_id = null`.
- The blanket `admin` middleware (any staff, any role) still gates all of `/admin/*`. Granular `permission:{key}` middleware (`App\Http\Middleware\EnsureUserHasPermission`) is applied **only** to `store`/`update`/`destroy` on roles/personnel and to `destroy` on users/transactions/groups/companies — read endpoints stay behind just `admin`. This is a deliberate scope boundary, not every route is permission-gated.
- `POST /admin/verify-password` is the back-office's step-up check, used by the delete-confirmation flow (see below) — not part of RBAC itself.

### Company: multiple per user, the real ownership boundary for almost everything
A user owns **1..N** `Company` records (`companies.user_id` is a plain FK, no longer unique) — each with its own fully isolated cash flow, product catalog, cash sessions, vault, and tontines. `transactions`, `products` (+ `product_categories`), `cash_sessions`, `vaults` (+ `vault_movements`), `groups` (+ `contributions`) all belong to `company_id`, not `user_id`. **The one deliberate exception**: `group_members` (tontine *membership*) stays person-based — `group_members.user_id` is unchanged, people still join tontines as themselves, the invite/join flow and member list are untouched. A `Group`'s `company_id` (chosen by the creator at creation, fixed for the tontine's lifetime) only decides financial attribution: which company's vault a payout credits (`TontinePayoutService::disburse()` credits `$group->company->vault`, **not** the resolved recipient member's own vault) and which company's `tontine_participation` credit-score factor a contribution counts toward. The vault's **PIN** is the other deliberate exception — see "Vault PIN", it's per-person, not per-company. "Solde" (the cash-flow balance shown on mobile) isn't a stored field — it's derived from transactions, so it's per-company automatically.
- **Data isolation**: every company-scoped mobile request carries a required `X-Company-Id` header, resolved and ownership-checked by `App\Http\Middleware\ResolveActiveCompany` (aliased `resolve-active-company`, wrapping the `/transactions`, `/products`, `/product-categories`, `/cash-sessions`, `/sync`, `/vault/*`, `/companies/{company}/credit-score` route group in `routes/api.php`) — 400 if missing, 403 if the company doesn't belong to the caller. The resolved `Company` is exposed via the `$request->company()` macro (`AppServiceProvider::boot()`), used everywhere these controllers previously called `$request->user()`. No silent fallback — missing/wrong header always fails loud, by design. `/groups/*` deliberately stays **outside** this group — a tontine carries its own `company_id` once created, and `POST /groups` takes `company_id` as a body field (a one-time choice, not an ambient "active company" concept the way transactions need).
- **Deleting a company is blocked while its vault holds a positive balance** (409, both `Api\CompanyController::destroy()` and `Api\Admin\CompanyController::destroy()`) — `vaults.company_id` cascadeOnDeletes like everything else, so this guard exists specifically to stop a company deletion from silently destroying real money.
- API: `GET/POST /companies` (`App\Http\Controllers\Api\CompanyController`) list/create — used both for first-time onboarding and for adding a 2nd+ company later via the mobile switcher; only sets `users.onboarding_completed_at` the first time. No edit/delete endpoint exists yet (deletion stays admin/back-office-only).
- Mobile: `mobile/src/context/company-context.tsx` (`CompanyProvider`, mounted between `AuthProvider` and `SyncProvider` in `_layout.tsx`) tracks `companies`/`activeCompany`, persists the active company id to SecureStore, and injects `X-Company-Id` into every request via `apiService.ts`'s `setApiActiveCompanyId()`. The switcher (`components/company-select-sheet.tsx`, opened from a chip in `tab-header.tsx`) resets navigation to the tabs root on switch rather than threading the active company into every pushed screen's fetch effect. Routing still checks the plain `onboarding_completed_at` column on `User` — unaffected by how many companies exist.
- Back-office: full CRUD-list (read/delete) at `/entreprises`, independent of mobile's onboarding flow.
- If `Company::CATEGORIES` changes, update it in four places: `api/app/Models/Company.php` (PHP const + DB enum in the migration), `mobile/src/services/companyService.ts`, `back-office/src/lib/company-categories.ts`.

### Business location (Congo-only, no country field)
`companies.department` is a DB enum of the Republic of Congo's **15 current departments** (`Company::DEPARTMENTS`) — restructured from 12 in October 2024 (Congo-Oubangui split from Cuvette, Nkéni-Alima from Plateaux, Djoué-Léfini from Pool). Congo-Brazzaville is confirmed the only real operating market today (seeded phone numbers, Yabeto's documented coverage, and `mobile/src/constants/countries.ts`'s own source comment all agree) — there's deliberately no country selector; add one only if/when that actually changes.
- `companies.city` is a **plain string, not an enum** — commune/arrondissement-level data is genuinely incomplete even in authoritative sources this soon after the reform, so pretending to a closed, validated list would risk silently-wrong data with false confidence. `Company::DEPARTMENT_CAPITALS` supplies the one verified-correct city per department as a one-tap onboarding default; picking "Autre" reveals free text — the exact same escape-hatch shape `category`/`other_category` already uses on this same model.
- Same 4-places-to-update rule as `CATEGORIES`: `Company::DEPARTMENTS`/`DEPARTMENT_CAPITALS`, `mobile/src/constants/congo-locations.ts`, `back-office/src/lib/company-locations.ts`.

### Products: per-merchant categories, cost/margin, stock as an audit trail
The product catalog (onboarding + `/products` screen) is a real ledger of inventory value and margin, not just a name/price list — this is the data a credit score (or a future lender) would actually want, feeding the same "financial identity" mission as everything else in this file.
- **Categories are per-merchant, not a fixed platform catalog** — `product_categories` (`ProductCategory` model) is a plain company-owned table, unlike `Company::CATEGORIES`/the permission catalog/scoring criteria (all fixed, code-defined lists). Seeded with sector-appropriate defaults at onboarding (`ProductCategory::seedDefaultsFor()`, reusing `ProductFactory::CATALOG`'s existing vocabulary), freely renamed/added/deleted after. Deleting a category `nullOnDelete()`s its products (uncategorizes, never cascade-deletes).
- **Stock costing is a single running weighted-average** (`products.cost_price`, recomputed on every `restock`) — a deliberate simplification, not FIFO/per-batch lot tracking, which would be real bookkeeping overhead a micro-business owner has no practical way to maintain by hand.
- **`stock_movements`** (restock/sale/adjustment, signed `quantity_change`, `unit_cost` snapshot) mirrors `vaults`/`vault_movements` — the only other "running balance + audit-trail movements" pattern in this codebase. `App\Services\ProductStockService` owns every stock/cost side-effect (mirrors `VaultController`'s exact transactional shape). `products.stock_quantity` is settable once at creation, then **only** changes via `restock`/`adjust-stock`/a sale — `PUT /products/{product}` doesn't accept it at all.
- **Restocking optionally logs a matching expense transaction** (`create_expense`, default on, category `achat_stock`) — ties inventory purchases into the same cash-flow ledger as everything else.
- **A sale snapshots `unit_cost` onto the transaction** (`ProductStockService::applyProductLink()`) uniformly whether or not the product tracks stock (so margin works for services too), and — for tracked products — decrements stock. **The insufficient-stock check is asymmetric on purpose**: blocking (422) on the online path (`TransactionController@store`), non-blocking on the offline sync path (`SyncController` — an offline sale already happened, so stock is allowed to go negative rather than stranding the sale unsynced). Manual `adjust-stock` stays blocking either way, since it's a deliberate correction, not an already-happened event.

### Admin endpoints are real; mobile-facing Day 2+ endpoints are still stubs
`Admin\*` controllers (`UserController`, `TransactionController`, `GroupController`, `CompanyController`, `RoleController`, `PermissionController`, `PersonnelController`, `StatsController`) are fully implemented — the back-office needs real data, so these moved out of TODO status. They return the full collection with no server-side pagination/filtering; the back-office's DataTable (see below) sorts/filters/paginates client-side, which is fine at seed-scale but would need revisiting for production. `Admin\UserController@show` eager-loads `companies.vault`/`role`/`groups` (no financial data — that moved to `Admin\CompanyController@show`, which eager-loads `user`/`transactions`/`products.category`/`cashSessions`); `GroupController@show` eager-loads `owner`/`company`/`members`/`contributions.user` — check there before adding a new endpoint for a "detail" need. Mobile-facing business logic (`TransactionController@store`, `VaultController@show/deposit/withdraw`, `GroupController@store/join/contribute`, `SyncController`) is fully implemented, not scaffolded — this note used to point at `// TODO (Day N): ...` stubs that no longer exist. `fintech-mvp-one-week-plan.md` remains the source of truth for what was originally in/out of scope, but treat "still TODO" claims about specific controllers as something to verify by reading the code, not assume.

### Back-office admin DataTable
`back-office/src/components/data-table/` is one reusable table (TanStack Table + shadcn) used by every list page (`users`, `transactions`, `groups`, `companies`, `personnel`): sorting, dynamic column visibility, Airtable-style per-column faceted filters, global search, pagination, row actions, and bulk actions. A page just defines `ColumnDef[]` (starting with `createSelectColumn()`) and a `facetedFilters` config, fetches its list via `back-office/src/services/adminService.ts`, and renders `<DataTable getRowHref={(row) => \`/utilisateurs/${row.id}\`}>` — see `src/pages/users.tsx` for the shortest example. **Rows themselves are the navigation affordance** — clicking a row (outside the `select`/`actions` cells, which stop click propagation) navigates to `getRowHref`. There is no "Voir les détails" row action; don't re-add one, just pass `getRowHref`.

**Deletion is step-up-authenticated, always** — `data-table/confirm-delete-dialog.tsx` (used by both `row-actions.tsx` and `bulk-delete-button.tsx`, and directly by the Personnel/Roles tabs): step 1, type the record's name/amount (or the keyword `SUPPRIMER` for bulk); step 2, re-enter your own password, verified via `POST /admin/verify-password` before the real `DELETE` fires. Never wire a delete button straight to `adminService.delete*` — go through `ConfirmDeleteDialog`.

**Detail pages** (`/utilisateurs/:id`, `/tontines/:id`, `/entreprises/:id`) use shadcn `Tabs` — except user-detail, which shrank to a plain stacked Informations + Sécurité layout (no `Tabs` chrome) once its financial tabs moved out. **Companies** are now the real per-entity financial data owner: Informations/**Score de crédit**/Transactions/Produits/Sessions de caisse/Analytique (one page-level `DateRangeFilter` drives Transactions + Analytique). **Users** get just Informations (a linked `Badge` per owned company — each now also showing that company's own vault balance, since the vault is per-company — plus a plain group count) and **Sécurité** (PIN lockout events stay user-linked, since the PIN itself is a per-person property — see "Vault PIN"). Groups get Informations (now also badging which company the tontine is attributed to)/Membres/Transactions/Analytique. `TransactionsTab`/`ProductsTab`/`CashSessionsTab`/`AnalyticsTab` (`components/user-detail/*`) are fully generic (plain array props, no user- or company-specific logic inside) and are reused verbatim by both user-detail (historically) and company-detail (now) — despite the folder name, they're not user-specific. The Analytique tabs reuse `dashboard/transactions-chart.tsx`, the new `dashboard/usage-chart.tsx` (transaction count per day), and `dashboard/tontines-chart.tsx` — the last one is a **generic ranked bar chart now reused three ways** (dashboard cotisations-per-tontine, group-detail cotisations-per-member, company-detail spend-per-category): its `tontine` data field is a historical name, not semantic — always pass `title`/`description` when reusing it.

### Credit scoring (the actual product mission: financial identity for informal businesses)
Scored **per company**, not per user — a merchant running two distinct businesses gets two distinct financial identities, not one blended one. `GET /companies/{company}/credit-score` (mobile, inside the `resolve-active-company` route group, plus its own independent `abort_unless($company->user_id === $request->user()->id, 403)` ownership check) and `GET /admin/companies/{company}/credit-score` (admin) both compute a 0–100 loan-admissibility score **live** (not cached) via `api/app/Services/CreditScoreService.php::calculate(Company $company)`, surfaced on the company detail page's "Score de crédit" tab. It's a weighted scorecard over a **fixed catalog of 6 factors** (`ScoringCriteriaSeeder::catalog()`: account age, transaction regularity, savings behavior, income/expense ratio, tontine participation, company profile) — same "fixed catalog, dynamic configuration" pattern as permissions, deliberately **not** a formula/rule engine (considered and rejected — see git history / prior session — as unnecessary complexity and attack surface for what's actually needed). `metricFor()` now reads every metric directly off the company itself — `account_age`/`transaction_regularity`/`income_expense_ratio` from `$company->transactions()`/`$company->created_at` as before, and `savings_behavior`/`tontine_participation` from `$company->vault?->balance`/`$company->contributions()->where('status','succeeded')->count()` (both now company-owned relations, no longer routed through the owner). `company_profile` is currently a **deactivated placeholder** (`is_active: false` in the seeder) — it used to be a "does this user have a company at all?" presence check, which became vacuous once `calculate()` always receives an existing company; repurposing it into a real "profile completeness" metric is a reasonable future follow-up, not yet done.
- Admins retune **weight**, **active/inactive**, and **band thresholds** (`[{min, max, points}]`) per factor from `/parametres` → "Notation de crédit" (`Admin\ScoringCriterionController@update`, behind `permission:settings.manage`) — adding a factor with a new metric needs code in `CreditScoreService::metricFor()`, same boundary as the permission catalog.
- Weights normalize across **active** criteria only — deactivating one doesn't skew the score, the rest just re-weight to fill 100%. Verified in this project by literally deactivating a criterion via curl and confirming the score changed and the factor dropped out of the breakdown.
- Verdict thresholds (`min_score_eligible`, `min_score_review`) live in the generic `settings` key-value table (`Setting` model, JSON `value`) — same table backs the "Général" tab's platform name/support email. New settings sections are a new seeded `key`, not a new table.
- **"Dossier de crédibilité financière"** — a server-rendered PDF (`GET /admin/companies/{company}/financial-dossier`, `Admin\CompanyController::financialDossier()`, `barryvdh/laravel-dompdf`) wrapping the same `CreditScoreService::calculate()` breakdown plus activity/vault/tontine stats, all company-direct (`App\Services\FinancialDossierService`). dompdf specifically because it's pure-PHP (no `wkhtmltopdf`/headless-Chrome system binary) — the production host is restrictive shared/cPanel hosting where installing a system binary isn't a safe assumption. `resources/views/pdf/financial-dossier.blade.php` is the server-side twin of mobile's client-generated `buildFinancialDossierHtml()` in `mobile/src/lib/pdf.ts` — same visual design (purple bands/boxes), written against dompdf's CSS subset (tables/inline-block, no flexbox) since dompdf can't render flex. Keep both in sync if the design changes on either side.
